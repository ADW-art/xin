## 二、详细漏洞分析

### V1 — JWT 密钥使用弱默认值 [严重]

**位置**：`backend/app/config.py:38` → `.env.example:25`

```python
jwt_secret_key: str = "change_this_to_random_string_32_chars"
```

**问题**：
- 默认值 `change_this_to_random_string_32_chars` 是典型的"占位符"字符串
- 如果部署时忘记修改 `.env`，攻击者可以本地伪造任意用户的 JWT Token
- JWT 算法为 HS256（对称加密），知道密钥即可签发任意 Token
- `.env.example` 中提示了需要修改，但在 `config.py` 中作为默认值会静默生效

**影响**：攻击者可伪造任意用户身份，访问所有 API，读取/修改任意用户画像和学习数据。

**修复建议**：
```python
# config.py
jwt_secret_key: str = ""  # 空字符串强制报错，而不是弱默认值

# 在 main.py 启动时校验
if not settings.jwt_secret_key or settings.jwt_secret_key == "change_this_to_random_string_32_chars":
    raise RuntimeError("JWT_SECRET_KEY 未设置或使用默认值，请修改 .env")
```

### V2 — TLS 证书验证全局禁用 [严重]

**位置**：`backend/app/services/spark_client.py:48-53`

```python
self._session = requests.Session()
self._session.trust_env = False
self._session.proxies = {'http': None, 'https': None}
self._session.verify = False  # ← 禁用 SSL 证书验证
import urllib3
urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)
```

**问题**：
- `verify=False` 使所有 HTTPS 请求不再验证服务器证书
- 任何人都可以发动中间人攻击（MITM），拦截/篡改与讯飞 API 的通信
- API Key 和用户对话内容在传输中可被窃取
- `urllib3.disable_warnings()` 只是隐藏了警告，没有解决安全问题

**同样的问题**在 `rag_service.py:46-51`：

```python
def _hf_session() -> requests.Session:
    session = requests.Session()
    session.verify = False  # ← 同样禁用了验证
    return session
```

**修复建议**：
```python
# 仅在开发环境允许跳过验证
import os
verify_ssl = os.getenv("ENV", "production") == "development"
self._session.verify = not verify_ssl

# 生产环境需确保系统 CA 证书包正确安装
# Windows: pip install pip-system-certs
```

### V3 — Docker 服务使用弱密码 [严重]

**位置**：`docker-compose.yml:7-10, 28-29`

```yaml
mysql:
  environment:
    MYSQL_ROOT_PASSWORD: root123    # ← 弱密码
    MYSQL_PASSWORD: a3_pass         # ← 弱密码

minio:
  environment:
    MINIO_ROOT_USER: minioadmin      # ← 默认用户名
    MINIO_ROOT_PASSWORD: minioadmin  # ← 默认密码
```

**问题**：
- MySQL root 密码 `root123` 是常见弱密码
- MinIO 使用官方默认凭据 `minioadmin/minioadmin`
- MySQL 端口映射到宿主机 `3307`，任何人可尝试连接
- MinIO 控制台暴露在 `9001` 端口
- Redis 无密码认证（`redis:7-alpine` 默认无密码）

**影响**：若宿主机端口对外开放，攻击者可直接访问数据库和对象存储。

**修复建议**：
- 所有密码改用 `.env` 变量注入，不在 `docker-compose.yml` 中硬编码
- Redis 添加 `requirepass` 配置
- 生产环境不映射数据库端口到宿主机（使用 Docker 内部网络通信）

### V4 — JWT 存储在 localStorage [高危]

**位置**：`frontend/src/api/index.ts:26` + `frontend/src/stores/user.ts:46`

```typescript
// api/index.ts
const token = localStorage.getItem('token')

// stores/user.ts
localStorage.setItem('token', accessToken)
```

**问题**：
- `localStorage` 可被任何 JavaScript 代码读取（包括 XSS 注入的恶意脚本）
- 与 `httpOnly` Cookie 不同，localStorage 没有内置的 XSS 防护
- 前端使用了 `v-html` 渲染 Markdown（`AssessmentView.vue:82`），虽经过 DOMPurify 净化，但 DOMPurify 历史上存在绕过漏洞

**修复建议**：
- 改用 `httpOnly` + `Secure` + `SameSite=Strict` Cookie 存储 Token
- 后端设置 Cookie 而非返回 JSON 中的 Token
- 保留当前方案但添加 CSP (Content-Security-Policy) Header

### V5 — 限流可被 X-Forwarded-For 欺骗绕过 [高危]

**位置**：`backend/app/core/rate_limit.py:38-42`

```python
def _get_client_ip(self, request: Request) -> str:
    forwarded = request.headers.get("X-Forwarded-For")
    if forwarded:
        return forwarded.split(",")[0].strip()  # ← 信任任意客户端提供的 IP
    # ...
```

**问题**：
- `X-Forwarded-For` 头部可被客户端任意设置
- 攻击者只需每次请求更换 `X-Forwarded-For` 值即可完全绕过硬编码为 500 的限流
- `X-Real-IP` 同样可被伪造
- 限流器使用内存存储，服务重启后计数清零

**修复建议**：
```python
def _get_client_ip(self, request: Request) -> str:
    # 仅在信任的反代后使用 X-Forwarded-For
    # 直连场景直接用 request.client.host
    if request.client:
        return request.client.host
    return "unknown"
```

### V6 — Token 黑名单降级逻辑安全漏洞 [高危]

**位置**：`backend/app/core/security.py:56-62`

```python
def is_token_blacklisted(jti: str) -> bool:
    try:
        import redis
        r = redis.from_url(settings.redis_url)
        return bool(r.exists(f"blacklist:{jti}"))
    except Exception:
        return False  # ← Redis 不可用时一律返回"不在黑名单"
```

**问题**：
- Redis 不可用时（如 Redis 宕机、网络故障），所有 Token 都被认为有效
- 攻击者可故意 DDoS Redis 使其不可用，然后使用已登出的 Token 继续访问
- 或自然情况：Redis 重启后缓存丢失，已登出 Token 重新可用

**修复建议**：
```python
except Exception:
    # Redis 不可用时应保守处理：拒绝所有已执行过登出操作的 token
    # 或至少记录日志并告警
    logger.error("Redis 不可用，黑名单检查降级 - 安全风险")
    return False  # 可接受但需告警
```

### V7 — CORS 配置过于宽松 [中危]

**位置**：`backend/app/main.py:38-44`

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=cors_origins,       # 默认 http://localhost:5173
    allow_credentials=True,
    allow_methods=["*"],              # ← 允许所有 HTTP 方法
    allow_headers=["*"],              # ← 允许所有请求头
)
```

**问题**：
- `allow_methods=["*"]` 允许任意 HTTP 方法（包括 DELETE/PUT/PATCH）
- `allow_headers=["*"]` 允许任意自定义头部
- 虽然 `allow_origins` 限制了来源，但方法/头部过于宽松增加了攻击面

**修复建议**：
```python
allow_methods=["GET", "POST", "PUT", "DELETE"],  # 明确列出
allow_headers=["Content-Type", "Authorization"],
```

### V8 — 文件上传无大小限制 [中危]

**位置**：`backend/app/api/admin.py:41-44`

```python
@router.post("/upload")
async def upload_document(
    file: UploadFile = File(...),  # ← 无 max_size 限制
    ...
):
    content = await file.read()  # ← 大文件会撑爆内存
```

**问题**：
- 没有限制上传文件大小，攻击者可上传 GB 级文件耗尽服务器内存
- `await file.read()` 会将整个文件读入内存
- 临时文件写入 `KB_DIR` 后解析失败才删除，攻击者可并发上传占满磁盘

**修复建议**：
```python
from fastapi import UploadFile

# 限制文件大小 50MB
MAX_UPLOAD_SIZE = 50 * 1024 * 1024

@router.post("/upload")
async def upload_document(
    file: UploadFile = File(..., max_length=MAX_UPLOAD_SIZE),
    ...
):
```

### V9 — 数据库密码明文写在 docker-compose.yml [中危]

**位置**：`docker-compose.yml:7-10`

**问题**：
- 凭证明文存储在版本控制中（`.env.example` 也是模板明文）
- 任何有仓库访问权限的人都能看到数据库密码
- 如果代码被 fork 或公开，凭据泄露

**修复建议**：
- 使用 Docker Secrets 或 `.env` 文件（不提交到 Git）
- `.env.example` 中写入占位符而非真实值
- 确认 `.env` 已在 `.gitignore` 中

### V10 — 代理和网络策略绕过 [中危]

**位置**：`backend/app/services/spark_client.py:48-49`

```python
self._session.trust_env = False
self._session.proxies = {'http': None, 'https': None}
```

**问题**：
- `trust_env = False` 忽略系统代理设置
- 在企业网络环境中，这会导致流量绕过安全代理/防火墙
- 如果这是为了方便开发而设的，生产环境不应保留

### V11 — 无 CSRF 保护 [中危]

**位置**：所有状态变更 API（`POST /api/auth/login`, `POST /api/auth/register`, `PUT /api/profile/me`, `POST /api/admin/upload` 等）

**问题**：
- 这些接口仅依赖 JWT Bearer Token（从 localStorage 读取，自动附加到请求头）
- 没有任何 CSRF Token 或 SameSite Cookie 保护
- 如果攻击者诱导用户访问恶意页面，可利用用户已登录状态伪造请求

**修复建议**：
- API 使用 `SameSite=Strict` Cookie + CSRF Token 双重保护
- 或利用 `X-Requested-With` / `Origin` / `Referer` 头部校验

### V12 — 内存限流器无上限 [低危]

**位置**：`backend/app/core/rate_limit.py:33`

```python
self._clients: dict[str, list[float]] = defaultdict(list)
```

**问题**：
- `_clients` 字典会随不同 IP 无限增长，永不清除已过期的客户端条目
- 攻击者可用大量伪造 IP 耗尽内存
- 没有定时清理过期条目的机制

**修复建议**：
```python
# 定期清理过期客户端
def _cleanup_expired(self):
    now = time.time()
    expired = [ip for ip, times in self._clients.items()
               if not times or now - times[-1] > self.window * 2]
    for ip in expired:
        del self._clients[ip]
```

### V13 — 前端无 Content-Security-Policy [中危]

**位置**：`frontend/index.html`

**问题**：
- HTML 中无 `<meta http-equiv="Content-Security-Policy">` 标签
- 无 CSP Header 配置（需后端配合或 Vite 插件）
- 一旦发生 XSS，攻击者可以执行任意内联脚本、加载外部资源
- localStorage JWT + 无 CSP = XSS → Token 窃取的完整攻击链

**修复建议**：
```html
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' http://localhost:*;
">
```

### V14 — 错误消息泄露到聊天界面 [中危]

**位置**：`frontend/src/views/ChatView.vue:408`

```typescript
store.appendToStreaming(`\n\n> **错误**: ${err.message}`)
```

**问题**：
- `err.message` 原始内容直接插入聊天界面
- 如果后端返回包含堆栈跟踪、文件路径、SQL 查询的错误信息，全部暴露给用户
- 信息泄露可用于后续针对性攻击

**修复建议**：
```typescript
// 显示用户友好的错误消息，不暴露原始错误
store.appendToStreaming(`\n\n> 处理请求时遇到问题，请稍后重试`)
```

## 五、结论

项目在**输入校验和内容安全**方面投入了超出预期的工程量（sanitize_input + ContentGuard + StreamGuard 三层防护），这在同类比赛中很少见。但**认证基础设施安全**存在几个低级但严重的问题：默认弱密钥、TLS 验证全局关闭、Docker 弱密码——这些都是部署到服务器后会被立即利用的漏洞。

**P0 三项修复总时间不超过 30 分钟**，强烈建议在提交前完成。
