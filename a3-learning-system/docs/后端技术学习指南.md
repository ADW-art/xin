## 二、讯飞星火客户端

> 文件: `backend/app/services/spark_client.py`

### 通信方式：WebSocket（不是 HTTP）

讯飞星火 API 不走普通 HTTP 请求，走 WebSocket——长连接、双向通信、服务端可以主动推送数据。这对流式输出至关重要：星火不是一次性返回完整答案，而是一段一段推送 token。

### 认证方式：HMAC-SHA256 签名

每次连接前，用 API Key + API Secret 生成一个签名，拼到 WebSocket URL 参数里。流程：

```
1. 取当前 UTC 时间（GMT 格式）
2. 拼签名原文: "host: spark-api.xf-yun.com\ndate: {时间}\nGET /v4.0/chat HTTP/1.1"
3. HMAC-SHA256(API_SECRET, 原文) → Base64 → signature
4. 拼 authorization 字符串 → Base64 → URL参数
5. 最终 URL: wss://spark-api.xf-yun.com/v4.0/chat?authorization=...&date=...&host=...
```

### 为什么每次都要签名

签名包含 UTC 时间戳，时间变了签名就变了，防止重放攻击（攻击者截获你的请求不能复用）。

### 两个方法

| 方法 | 返回方式 | 用途 |
|------|---------|------|
| `chat_stream()` | Generator，逐段 yield | SSE 流式推给前端 |
| `chat_sync()` | 等全部生成完返回完整文本 | Supervisor 意图分类（需要完整 JSON） |

### 流式响应解析

星火的 WebSocket 响应格式：

```json
{
  "header": {"code": 0, "message": "success"},
  "payload": {
    "choices": {
      "status": 1,          // 0=首帧 1=中间帧 2=尾帧
      "text": [{"content": "Python"}]
    }
  }
}
```

`chat_stream()` 里循环 `ws.recv()` → 解析 JSON → yield content → `status==2` 时停止。

### 你需要了解的

- WebSocket 连接的生命周期：建立 → 发请求 → 循环接收 → status=2 关闭
- HMAC 签名原理：用密钥搅拌原文，生成防篡改的哈希
- Generator 函数：`yield` 关键字让函数可以多次返回值

## 三、多智能体协作

> 文件: `backend/app/agents/` 目录下全部 7 个文件

### 6 个 Agent 的职责

| Agent | 文件 | 触发场景 | 核心能力 |
|-------|------|---------|---------|
| **Supervisor** | `supervisor.py` | 每次对话入口 | 意图分类 → 路由决策 |
| **Profile** | `profile_agent.py` | 自我介绍/背景 | 6维画像对话采集 → MySQL持久化 |
| **Resource** | `resource_agent.py` | 想学XX/生成资料 | RAG检索 + 5种资源生成 |
| **Question** | `question_agent.py` | 做题/测试 | BKT自适应难度出题 |
| **Path** | `path_agent.py` | 学习计划 | 知识图谱拓扑 + 艾宾浩斯复习 |
| **Evaluation** | `evaluation_agent.py` | 评估/报告 | BKT数据 + 6维评估 |

### 共享状态 AgentState

```python
# state.py
class AgentState(TypedDict):
    messages: list[BaseMessage]      # 对话历史（LangGraph自动追加）
    current_agent: str               # 当前活跃Agent
    next_agent: Optional[str]        # Supervisor的路由决策
    user_profile: Optional[dict]     # 6维画像
    context: dict                    # {"topic": "Python", ...}
    agent_outputs: dict              # 各Agent输出缓存（含stream_pending）
    stream_buffer: str               # SSE流式缓冲区
    user_id: int                     # JWT解析的用户ID
```

所有 Agent 共享同一个 State 字典，Agent 之间通过修改 State 来传递信息。比如 Profile Agent 把采集到的画像写入 `user_profile`，Resource Agent 生成资源前从 `user_profile` 读取学生偏好。

### Supervisor 路由逻辑

```
用户输入 → 调星火 chat_sync 做意图分类 → 返回 JSON {"intent": "...", "params": {...}}
         → route_map 映射:
            "profile"    → profile_agent
            "resource"   → resource_agent
            "question"   → question_agent
            "path"       → path_agent
            "evaluation" → evaluation_agent
            "chat"       → END（直接结束）
```

### 流式生成模式 (stream_pending)

大部分 Agent 不自己调星火生成内容，而是返回一个 `stream_pending` 对象：

```python
"agent_outputs": {
    "resource_agent": {
        "type": "document",
        "topic": "Python装饰器",
        "stream_pending": {
            "messages": [{"role": "system", "content": "..."}],  # 构造好的Prompt
            "temperature": 0.7,
            "max_tokens": 2048,
        },
    },
}
```

`chat.py` 里的 `event_stream()` 检测到 `stream_pending`，调用 `_bridge_stream()` 实际执行星火调用和 SSE 推送。这样设计的好处：Agent 只负责构造 Prompt，流式推送的统一逻辑在 chat.py 一处维护。

## 四、BKT 贝叶斯知识追踪

> 文件: `backend/app/services/bkt_service.py`
> 这是项目的**核心自研算法**，答辩时的学术深度担当。

### 问题背景

传统的"自适应出题"是这样做的：

```
if 连对2次: 升难度
elif 答错1次: 降难度
```

问题是：学生瞎猜对了也算"对"，会的题手滑做错了也算"错"。简单规则无法区分"真会"和"猜对"。

### BKT 的核心思想

**不只看答题对错，而是用贝叶斯公式推断学生"真正掌握"的概率。**

每个知识点维护一个 **P(known)**——学生真正掌握这个知识点的概率。每次答题后，不直接判断"会了"或"不会"，而是**更新这个概率**。

### 四参数模型

| 参数 | 符号 | 默认值 | 含义 |
|------|------|--------|------|
| 初始掌握概率 | P(L0) | 0.3 | 还没学时，30%概率已经会了 |
| 学习率 | P(T) | 0.4 | 每次学习/练习后，从不会到会的概率 |
| 猜测率 | P(G) | 0.2 | 没掌握但瞎猜对的概率 |
| 失误率 | P(S) | 0.1 | 掌握了但手滑做错的概率 |

### 贝叶斯更新公式

**答对时：**

```
                         P(known) × (1 - P(S))
P(known|correct) = ──────────────────────────────────
                    P(known)×(1-P(S)) + (1-P(known))×P(G)
```

分子 = 真正会且没失误的概率
分母 = 分子 + 不会但猜对的概率

**答错时：**

```
                       P(known) × P(S)
P(known|wrong) = ──────────────────────────────────
                  P(known)×P(S) + (1-P(known))×(1-P(G))
```

分子 = 真正会但失误了的概率
分母 = 分子 + 不会也没猜对的概率

### 学习效应

答对后除了贝叶斯更新，还额外加上学习效应：

```python
if is_correct:
    p_known += (1 - p_known) * p_learn  # p_learn = 0.4
```

这模拟了"做对一道题后，对这个知识点的掌握确实增强了"。

### 难度决策表

```
P(known) < 0.35  → 简单
0.35 ~ 0.6       → 中等
0.6 ~ 0.85       → 较难
> 0.85           → 挑战  (视为已掌握)
```

### 代码结构

```python
class KnowledgeNode:       # 单个知识点的 BKT 状态
    p_known: float          # 当前掌握概率
    update(is_correct)      # 贝叶斯更新
    is_mastered: bool       # P > 0.85
    level: str              # 入门/学习/熟悉/精通

class BKTTracker:           # 全局追踪引擎
    get_or_create(concept)  # 获取或创建知识点
    record_answer(concept, is_correct)  # 记录答题
    get_difficulty(concept) # 推荐难度
    get_mastered()          # 已掌握列表
    get_weak_points()       # 薄弱点列表
```

### 答辩话术参考

> "我们借鉴了教育测量学中 Corbett & Anderson 1995 年提出的知识追踪理论，实现了一个四参数贝叶斯模型。四个参数分别建模初始知识状态、学习效率、猜测行为和失误行为。每次答题后，用贝叶斯后验概率更新对每个知识点的掌握度估计，而非简单的'连对升连错降'。"

## 五、知识图谱 + 拓扑排序

> 文件: `backend/app/services/knowledge_graph.py`
> 第二个自研算法。解决"先学什么后学什么"的科学排序问题。

### 为什么不能让 LLM 直接排

LLM 可以生成学习路线，但它靠的是训练数据里的模式匹配，可能：
- 把不存在的前置关系编造出来
- 漏掉真正必须的先修知识
- 给不出排序的数学依据

自研知识图谱的好处：**从教材中自动提取依赖关系，拓扑排序有严格的数学保证。**

### 算法流程

```
教材文本（多章多节）
    │
    ▼
① 知识点提取
   ├── jieba 分词（中文）+ 正则（英文）
   ├── 标题权重 ×3，首段权重 ×2
   ├── 停用词过滤（200+ 中英文停用词）
   └── TF-IDF 取 Top-15 关键词 → 每个词是一个知识点节点
    │
    ▼
② 依赖关系构建
   ├── 遍历每个段落，找出同时出现的知识点
   ├── 按出现顺序：先出现的 → 后出现的（建立有向边）
   └── 共现频率越高，依赖关系越强
    │
    ▼
③ 构建有向无环图（DAG）
   知识图谱类 KnowledgeGraph:
     edges: dict[str, set[str]]     # 前置 → {后置, ...}
     in_degree: dict[str, int]      # 入度（几个前置）
     keyword_weights: dict[str, float]  # 知识点权重
    │
    ▼
④ 拓扑排序
   1. 找出所有入度=0的节点 → 第1阶段（无前置依赖）
   2. 移除这些节点，更新入度
   3. 重复找入度=0 → 第2阶段 → 第3阶段 → ...
   4. 跳过用户 BKT 已掌握的知识点
    │
    ▼
⑤ 时间估算
   每个知识点 1.5 小时 × 节点数 ÷ 用户每周投入时间 → 预计周数
    │
    ▼
⑥ 插入艾宾浩斯复习节点 → 最终路径
```

### 拓扑排序图解

```
知识点图:
  变量(入度0) ──→ 函数(入度1) ──→ 装饰器(入度2)
                              ↗
  闭包(入度0) ──────────────→

拓扑排序结果:
  第1阶段: [变量, 闭包]     ← 入度为0，无前置依赖
  第2阶段: [函数]           ← 前置(变量)已学
  第3阶段: [装饰器]         ← 前置(函数+闭包)已学
```

### 循环依赖处理

如果检测到环（死锁），取入度最小的节点先行打破循环，打印 warning 日志。

## 六、艾宾浩斯遗忘曲线

> 文件: `backend/app/services/review_scheduler.py`

### 数学模型

遗忘曲线公式：

```
R = e^(-t / S)

R = 记忆保留率 (0~1)
t = 距上次学习的天数
S = 记忆强度（初始 0.5，每次复习 +0.15，上限 2.0）
e = 自然常数 2.718...
```

**直观理解**：时间 t 越大，e^(-t/S) 越小，记忆越模糊。记忆强度 S 越大，遗忘越慢。

### 间隔递增复习法 (Spaced Repetition)

```
复习间隔序列: [1天 → 3天 → 7天 → 14天 → 30天 → 90天]

第1次学习后 → 1天后复习
第2次复习后 → 3天后复习（间隔拉长）
第3次复习后 → 7天后复习
...
```

每次复习后间隔推进到下一级，同时记忆强度 S 增加 0.15。

### 三级遗忘风险

```
R < 0.5  → 高风险 → "立即复习"（已经忘了一半以上）
R < 0.7  → 中风险 → "建议近期复习"
R ≥ 0.7  → 安全
```

### 在 Path Agent 中的使用

Path Agent 生成学习路径时，自动查询哪些知识点到了复习窗口：

```python
scheduler = get_scheduler()
due_reviews = scheduler.get_review_nodes()
# → [{"concept": "装饰器", "retention": 0.42, "risk": "high", ...}, ...]
```

把这些复习节点插入学习路径中，提醒学生在遗忘临界点复习。

## 七、RAG 混合检索

> 文件: `backend/app/services/rag_service.py`
> 详细讲解见 `docs/RAG设计思路详解.md`

### 一句话概括

**用户提问 → 从教材库里检索最相关段落 → 和问题一起给星火 → 星火基于教材回答（不瞎编）**

### 三路融合流程

```
用户查询: "Python装饰器怎么实现"
        │
        ├── ① 稠密向量召回 (BGE-M3 → FAISS/ChromaDB) → Top-30
        │     擅长语义理解，"代码优化"能匹配"性能调优"
        │
        ├── ② BM25 稀疏召回 (jieba分词 + TF-IDF) → Top-30
        │     擅长精确匹配，"@property"不会漏
        │
        ├── ③ RRF 融合 (Reciprocal Rank Fusion, k=60) → Top-15
        │     formula: RRF_score = Σ 1/(60 + rank_i)
        │
        ├── ④ Cross-Encoder 精排 (BGE-Reranker-v2-m3) → 逐对打分
        │     同时读查询和文档，判断语义匹配度（最精确但最慢）
        │
        └── ⑤ 返回 Top-7 最终结果
```

### 防幻觉策略

Prompt 里加入约束 + 引用标注：

```
参考教材：
[来源：Python官方文档 第5章]
装饰器是一种高阶函数，接受函数作为参数并返回新函数...

你必须严格遵守：
1. 优先使用参考教材中的知识点组织内容
2. 如果参考资料中有相关内容，可以直接引用并标注来源
3. 不要编造教材中没有的概念、函数名或代码示例
```

## 八、FAISS 多子索引

> 文件: `backend/app/services/faiss_client.py`

### 为什么需要 FAISS

ChromaDB 是独立服务（Docker 容器），每次检索走 HTTP 网络调用。FAISS 是 Python 库（进程内），C++ 实现，检索速度远超 ChromaDB。

### 多子索引架构

按学科划分独立索引，检索时先路由：

```
faiss_indices/
├── python.faiss        ← Python 相关教材
├── datastructure.faiss ← 数据结构教材
├── os.faiss            ← 操作系统教材
├── network.faiss       ← 计算机网络教材
├── database.faiss      ← 数据库教材
├── ai_ml.faiss         ← AI/机器学习教材
├── clang.faiss         ← C/C++教材
├── java.faiss          ← Java教材
├── math.faiss          ← 数学基础教材
└── default.faiss       ← 未分类教材（兜底）
```

### 路由逻辑

```python
SUBJECT_MAP = {
    "python": "python",
    "数据结构": "datastructure",
    "人工智能": "ai_ml",
    "c语言": "clang",
    ...
}

def route(subject):       # "Python装饰器" → "python" 子索引

### 索引类型：IndexFlatIP

## 十、SSE 流式桥接

> 文件: `backend/app/api/chat.py` → `_bridge_stream()` 函数

### 问题：同步 WebSocket vs 异步事件循环

```
星火 chat_stream(): 同步阻塞（ws.recv()卡住线程等数据）
FastAPI SSE:        异步生成器（async for 在事件循环中跑）

矛盾: 同步函数不能直接放在异步环境里跑——会阻塞整个事件循环！
```

### 解决方案：线程桥接

```
                     ┌─────────────────────┐
                     │   线程池 (1线程)      │
                     │   spark.chat_stream() │
                     │   ws.recv() 阻塞等待  │
                     │        │              │
                     │   chunk1, chunk2, ... │
                     │        │              │
                     │   call_soon_threadsafe│
                     │        │              │
                     └────────┼──────────────┘
                              │
                     ┌────────▼──────────────┐
                     │   asyncio.Queue        │
                     │   (线程安全队列)        │
                     └────────┬──────────────┘
                              │
                     ┌────────▼──────────────┐
                     │   主事件循环            │
                     │   async for chunk in   │
                     │   _bridge_stream():    │
                     │       yield SSE event  │
                     └──────────────────────┘
```

### 关键 API

```python
loop.call_soon_threadsafe(queue.put_nowait, chunk)
# 在事件循环的下一个 tick 把 chunk 放入异步队列
# "线程安全" = 不持有 GIL 时不冲突
```

### 代码结构

```python
async def _bridge_stream(spark, messages, temperature, max_tokens):
    queue = asyncio.Queue()       # 线程安全桥梁
    loop = asyncio.get_event_loop()

    def _run():                   # 在线程池里跑
        try:
            for chunk in spark.chat_stream(messages, ...):
                loop.call_soon_threadsafe(queue.put_nowait, chunk)
        finally:
            loop.call_soon_threadsafe(queue.put_nowait, _SENTINEL)

    ThreadPoolExecutor(max_workers=1).submit(_run)

    while True:
        item = await queue.get()  # 异步消费
        if item is _SENTINEL: return
        if isinstance(item, Exception): raise item
        yield item                # SSE逐段推送
```

## 十二、JWT 认证流程

> 文件: `backend/app/core/security.py` + `backend/app/api/auth.py`

### 注册流程

```
POST /api/auth/register {username, password, nickname}
    → 检查用户名是否已存在
    → bcrypt 哈希密码
    → INSERT users 表
    → 生成 JWT（sub=user_id）
    → 返回 {"access_token": "eyJ..."}  ← 注册即登录
```

### 登录流程

```
POST /api/auth/login {username, password}
    → 查 users 表
    → bcrypt.verify(明文, 哈希) 比对密码
    → 生成 JWT → 返回
```

### JWT 结构

```
Header:  {"alg": "HS256", "typ": "JWT"}
Payload: {"sub": "1", "username": "zhangsan", "exp": 1750000000}
Signature: HMAC-SHA256(Header.Payload, JWT_SECRET_KEY)
```

### 请求认证

```
前端:  Authorization: Bearer eyJ...
          ↓
后端:  decode_access_token(token[7:])  → 解析 payload
          ↓
       db.query(User).filter(id=payload["sub"])  → 拿 User 对象
          ↓
       注入到路由函数 current_user 参数
```

### Chat 接口的"可选认证"

Chat 接口允许未登录用户使用（`_optional_user` 依赖）：

```python
def _optional_user(authorization = Header(None)):
    if not authorization:          # 没带 token → 返回 None
        return None
    payload = decode_access_token(...)
    user = db.query(User)...       # 带了 token → 解析用户
    return user
```
