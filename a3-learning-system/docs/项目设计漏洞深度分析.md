## 二、逐模块设计漏洞

### 2.1 错误处理 — 132 处 `except Exception` 吞错

**严重程度: 🔴 高**

对标 LangGraph 官方示例——每个节点有明确的错误边界和降级路径。当前项目:

```python
# 当前: 所有异常一把抓, 丢失堆栈信息
except Exception as e:
    logger.warning("xxx失败: %s", e)  # 仅记录, 不处理

# 标准做法(LangGraph pattern):
try:
    result = llm.invoke(messages)
except (RateLimitError, APITimeout) as e:
    # 可恢复错误 → 重试
    return Command(goto="retry_handler", update={"error": str(e)})
except (AuthenticationError, InvalidRequestError) as e:
    # 不可恢复 → 降级
    return Command(goto="fallback", update={"error": str(e)})
```

**影响**: 132 处吞错导致生产环境排障几乎不可能。答辩演示时任何异常都变成静默降级，用户看不到错误但功能异常。

**修复建议**: 
1. 定义 `AppError` 异常层级: `RecoverableError` (RateLimit/Timeout) / `NonRecoverableError` (Auth/Config) / `DegradedError` (RAG不可用)
2. Agent 节点增加 `error` 状态字段(AgentState 已预留但未使用)
3. 关键路径加 Sentry-style 错误上下文

### 2.2 API 调用无重试机制

**严重程度: 🔴 高**

```python
# spark_client.py:93 - 单次调用, 失败即抛
resp = requests.post(url, json=payload, headers=headers, timeout=60)
resp.raise_for_status()
```

对标: LangGraph 官方示例使用 tenacity/backoff 库，3次指数退避重试。

**影响**: 网络抖动/API限流 → 整个请求链路中断。答辩现场网络不稳定 = 演示失败。

**修复建议**:
```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=1, max=10))
def _call_api(self, messages): ...
```

### 2.3 LangGraph 设计偏离官方最佳实践

**严重程度: 🟡 中**

| 官方实践 | 当前实现 | 偏离程度 |
|----------|---------|:--:|
| Agent 节点返回 `Command(goto=...)` | 返回 dict 手动设 `next_agent` | 中 |
| `interrupt()` 实现 HITL | 无任何 interrupt | 高 |
| 使用 LangGraph Store 跨会话记忆 | 无 Store, 仅 MemorySaver | 中 |
| 节点编译时类型校验 (Pydantic) | TypedDict → dict 手动转换 | 低 |
| 子图(subgraph)模式复用 | 无子图, 每个Agent是独立函数 | 低 |
| tracing via LangSmith/LangFuse | 自建 trace API (不完整) | 中 |

**最大偏离**: 无 HITL (Human-in-the-Loop)。LangGraph 的核心卖点就是 `interrupt()` 暂停→人工审核→恢复。评分标准中智能辅导/评估检测都需要人工介入的场景。

**修复建议**: 
- 在 Supervisor 检测到 "低置信度意图" 时 → `interrupt()` → 前端展示"我不确定你想做什么, 是要学习/做题/评估?"
- 在资源生成后 → `interrupt()` → 前端展示"生成的资源是否满意? 不满意可以重新生成"

### 2.5 并发与线程安全

**严重程度: 🟡 中**

```python
# chat.py:626
ThreadPoolExecutor(max_workers=1).submit(_run)
```

每次 SSE 请求创建一个新线程池——对标 FastAPI 最佳实践应该用 `asyncio.to_thread()` 或全局线程池复用。

```python
# dependencies.py:14-37
_spark_client: SparkClient | None = None  # 模块级单例, 非线程安全
```

虽然 SparkClient 内部无可变状态，但 `requests.Session` 非线程安全。

**修复建议**: SparkClient 使用 `threading.local()` 或改为完全无状态。

### 2.6 前端 Store 设计 — learning.ts 数据流断裂

**严重程度: 🟡 中**

对标 Vue3 + Pinia 最佳实践——Store 应作为组件间共享数据的唯一入口。

当前 `learning.ts` (953行) 确实封装了 API 调用，但各 View 仍有直接的 API import:

```typescript
// LearningPathView.vue 直接调 api
const r = await api.get('/path/graph/' + currentDomain.value)
// Dashboard.vue 也直接调 api
const r = await api.get('/profile/me')
```

**影响**: 数据流不统一——Store 有数据但 View 绕过 Store 直接请求 → 缓存失效 → 重复请求。

**修复建议**: 所有 View 的数据获取统一走 `useLearningStore().fetchXxx()` 或 `useUserStore().fetchXxx()`。

### 2.7 Agent 间内存泄漏风险

**严重程度: 🟢 低**

```python
# question_agent.py:34
_last_questions_cache: dict[int, tuple[str, float]] = {}
```

TTL 1h + max 128 条已加(上轮修复)，但其他模块仍有类似裸 dict 缓存：

- `bkt_service.py`: `_tracker_cache: dict[int, BKTTracker]` — 无 TTL, 用户下线后 tracker 对象永远不会被回收
- `review_scheduler.py`: `_scheduler_instances: dict[int, ReviewScheduler]` — 同上

**修复建议**: 全部改为 `functools.lru_cache` 或 `cachetools.TTLCache`。

### 2.8 输入校验 — 基础好但缺深层防御

**严重程度: 🟢 低**

```python
# chat.py:51-59
@field_validator("content")
def content_must_be_meaningful(cls, v: str) -> str:
    if len(v.strip()) > 4000: raise ValueError("消息内容不能超过4000字")
    return sanitize_input(v)
```

有基础校验(长度/SQL/XSS)。但缺少:
1. Unicode 规范化 — 同形异义字攻击 (unicode confusable detection)
2. Prompt injection 检测 — 用户说 "忽略你的系统提示" → 无过滤

ChatInput `maxlength=4000` 限制好但应加 `show-word-limit`。

### 2.9 ChatView SSE 缺陷

**严重程度: 🟡 中**

`ChatView.vue` 流式对话时:
1. 用户发送消息后输入框未立即清空 → 用户可能重复点击发送
2. 流式输出进行中用户无法中断 (无 Stop 按钮——参考 ChatGPT 设计)
3. 滚动到底部逻辑: `scrollTop = scrollHeight` 在 content 快速变化时卡顿

**修复建议**: 发送后立即禁用按钮 + 添加 Stop 按钮 (`AbortController`) + `requestAnimationFrame` 平滑滚动。

---

### 2.10 BktCenter 缺少真实数据闭环

**严重程度: 🟡 中**

`BktCenter.vue` (38KB / 700+行) 有自己的前端 BKT 贝叶斯模拟——这很好！但缺点:
1. 前端模拟的后端公式与实际 BKT v4 公式可能不一致 (v4 新增 P(T)双向施加 + P(F) 遗忘)
2. API 调 `/api/bkt/status` + 降级到 `/api/profile/me`，但"答题演示"是纯前端 JS 计算，不是真实 BKT v4
3. 缺少 `/api/bkt/answer` 返回的 `update_step` 分步明细展示

**修复建议**: BktCenter 答题演示改为调 `/api/bkt/answer` 获取真实 update_step 并渲染贝叶斯推导过程。
