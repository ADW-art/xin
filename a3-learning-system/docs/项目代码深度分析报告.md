## 二、逐模块深度评价

### 2.1 监督器路由 (supervisor.py:319-637)

**实际采用策略：规则优先 → LLM兜底 → 关键词级联**

```
输入消息
  ↓
_is_keyword_fallback()  ← 60+关键字四级优先级（行212-278）
  ↓ 结果为"chat"时
LLM意图分类  ← 星火API + JSON提取 + regex降级（行548-575）
  ↓
路由决策  ← 5个Worker Agent或END
```

**强项：**

- 确定性路由节省API成本。`_keyword_fallback` (行212-278) 覆盖了常见学习场景，只有真正模糊的输入才触发LLM调用。这是工程上务实的做法。
- 教学流程自动推进 (行378-432) 实现了阶段内自动继续、阶段边界暂停询问、3节点安全上限的完整状态机。这比简单的"教完一个继续下一个"要精细得多。
- `_proactive_suggest` (行281-315) 在Agent完成后主动推荐下一步——例如教学完成→建议练习，评估完成→建议针对性学习。

**弱项：**

- 关键词匹配存在大量误报风险。`_is_broad_learning_request` (行145-193) 中`broad_markers`包含`"学"`这样的单字，任何包含"学"的消息都会被判定为学习请求。"数学"、"同学"、"放学"都会触发。
- `_keyword_fallback`中的`"做"`关键字 (行262) 匹配`cognitive_style`维度，但"怎么做"、"做什么"等日常用语也会误触发profile采集。
- 两个profile_agent完成后的处理块 (行357-374 和 行434-461) 逻辑部分重叠：第一个处理`profile_first`标记的特定流程，第二个处理通用的`deferred_intent`路由。两个块共享相同的触发条件(`current_agent == "profile_agent"`)，阅读时需要仔细追踪`profile_first`是否被设置才能判断哪个块生效。

**参照对比：** LangGraph官方supervisor示例使用纯LLM路由，本项目采用的"规则优先+LLM兜底"在成本和响应速度上更优，但规则维护成本随场景增长。

### 2.2 Resource Agent (resource_agent.py:32-607)

**系统中质量最高的Agent。**

**强项：**

- 系统提示 (行32-162) 包含：具体的反幻觉规则（行41-48："不要猜测代码输出"、"禁止在注释中写#输出："）、好坏示例对比、强制6部分检查清单（行145-160）、题型格式约束（行110-121的question_set严格JSON格式）。
- RAG检索 + Content Store降级 + 纯LLM兜底的三级知识注入策略 (行403-431)，保证在任何基础设施状态下都能生成内容。
- 用户显式请求覆盖画像偏好的机制 (行440-463)，例如用户说"生成思维导图"时覆盖默认的text类型。

**弱项：**

- 系统提示130行，每次调用消耗约1200 token。其中"强制检查清单"（行146-160）与正文（行58-143）有内容重复——同样的规则被说了两遍。
- RAG查询字符串被语言标注污染 (行383-387→行409)：用户想学"C++指针"时，RAG查询变成"C++指针（使用C++语言）"，括号内的标注对向量检索无意义且可能降低召回质量。
- RAG未就绪时静默降级 (行414-415)，仅在日志中记录，用户不知道生成质量下降。

### 2.3 Question Agent (question_agent.py:32-466)

**实现双模式（出题/评阅）的完整工作流。**

**强项：**

- 答案格式检测 (行70-96) 覆盖11种正则模式，包括"1A"、"1 A"、"选A"、"答案是："、Python代码答案、列表答案等。这是对真实学生输入多样性的认真处理。
- 题目文本缓存 (行34-65) 解决了Agent不自行调用LLM后评阅模式需要题目原文的问题。TTL 24小时（已修复）、容量上限128条、自动淘汰机制。
- 难度自适应 (行193-198的generate prompt)：连续对2次→升难度，错1次→降难度，正确率≥80%→推荐进阶。

**弱项：**

- `extract_answer_map` (行99-127) 对自然语言答案无效。学生写"我觉得第一题选A第二题选B"时，正则全部失配，`result`为空字典。
- `parse_grading_result` (行431-459) 的严格正则要求LLM精确输出`## 第 1 题：正确`格式。LLM输出`## 题目1: 正确`或`### 1. 对`时正则失配，触发猜解算法 (行451-459)：按总分拆分为`[True]*correct + [False]*(total-correct)`，丢失每题级别的正误信息。
- 缓存过期后从对话历史恢复 (行275-283，已修复添加) 的匹配条件`'题目' in m.content[:200]`是脆弱的启发式——前200字符不含"题目"的assistant消息会被跳过。

### 2.4 Path Agent (path_agent.py:28-877)

**系统中最复杂的Agent，877行。**

**强项：**

- 完整的教学循环状态机：`_teaching_init`(行362)→`_teaching_advance`(行488)→Supervisor链式路由→Resource Agent生成内容→循环。4个阶段的状态转换清晰。
- 多学科知识图谱加载 (行170-289)：支持按topic关键词匹配领域文件，未匹配时加载全部KG作为兜底。
- 拓扑排序集成BKT掌握状态 (行292-308)：已知知识点标记为done，未知的按拓扑序排列。

**弱项：**

- `_select_domain_files` (行170-201) 使用硬编码的关键词映射表。`"c语言"`→`kg_cpp.json`（行176-177），`"指针"`→C++ KG（行173），这些都是不精确的启发式。新增学科需要修改代码。
- `_compute_topology` (行292-308) 将BKT的`get_mastered()`列表传给KG的`topological_sort()`，但两个系统的概念名可能不匹配。BKT节点名来自答题时的topic参数，KG节点名来自JSON文件。只有经过`normalize_concept_name`（已在P0修复中添加）的概念才能对齐。
- 无动态重规划：路径在`_teaching_init`时确定，后续BKT更新不会触发路径调整。学生通过教学掌握了前置知识后，后续节点顺序不会重新优化。
- 教学自动推进在阶段边界暂停时（行411-421），没有生成结构化的"下一阶段选项"——只是停止并等待用户说"继续"。

### 2.5 Evaluation Agent (evaluation_agent.py:17-262)

**强项：**

- 系统提示 (行17-89) 包含Mermaid饼图要求、明确的禁止项（"禁止：'你的基础知识还不错'"、"禁止：维度分数与饼图数据不一致"）、维度编号对应关系。
- 维度分数计算已修复（P1）：focus改从实际活跃天数推算，logic改从BKT变异系数推算，trend不再与knowledge相同。

**弱项：**

- `_compute_speed_score` (行97-129) 衡量的实际上是**答题量**而非**学习速度**。公式`q_per_day * 5`映射到0-100：日答20题=100分，日答10题=50分。一个快速掌握但只答了5题的学生得到低分，一个刷了大量简单题的学生得到高分。
- 修复前的logic_score（`accuracy_rate*0.5+mastered_rate*0.5`）曾是knowledge的线性组合，两者相关系数接近0.9。修复后使用BKT变异系数，但知识点数<2时仍退化为50分默认值。

### 2.6 Profile Agent (profile_agent.py:32-372)

**强项：**

- 渐进式采集：通过对话逐轮收集1-2个维度（行197-310的采集逻辑），避免一次问太多让用户反感。
- `KB_BLACKLIST` (行23-29) 过滤了13个常见的LLM泛化回复（"有待进一步了解"、"目前尚未掌握"等），防止空值写入画像。

**弱项：**

- `_compute_dimension_scores` (行92-130，已修复) 的评分逻辑本质上是启发式的。knowledge_score基于话题数量和关键字匹配，而非实际测试结果。logic_score仅从cognitive_style的关键字推导。这些分数在BKT数据积累前用作先验还可以接受，但与BKT的真实贝叶斯后验混用时会产生矛盾。
- `_build_summary` (行133-167) 和`_compute_dimension_scores`对`knowledge_base`的读取路径不同——前者处理dict和string两种类型，后者只处理dict（已修复前只处理string）。类型不一致是Bug的来源。

## 三、BKT知识追踪 — 系统最强模块

### 3.1 数学实现 (bkt_service.py:78-84, 617-892)

```
四参数模型:
  P(L₀) = 0.3  初始掌握概率
  P(T)  = 0.2  学习转移概率（每次答题后的学习增益）
  P(G)  = 0.15 猜测概率（不会但猜对）
  P(S)  = 0.1  失误概率（会但答错）
  P(F)  = 0.0  遗忘概率（暂未启用）

贝叶斯更新:
  答对后: P(known|correct) = P(known)*(1-P(S)) / [P(known)*(1-P(S)) + (1-P(known))*P(G)]
  答错后: P(known|wrong)   = P(known)*P(S) / [P(known)*P(S) + (1-P(known))*(1-P(G))]
  然后:   P(known) = 后验 + (1-后验)*P(T)
```

测试`test_bkt_v4.py:100-112`包含手算验证：`numerator = 0.3 * (1 - 0.1) = 0.27`，`denominator = 0.27 + 0.105 = 0.375`，`posterior = 0.72`。这是教科书级别的测试。

EM参数拟合 (行700-892) 采用坐标下降+多起点（6组随机种子）+黄金分割搜索。收敛到局部最优的精度在`test_bkt_v4.py:330-380`中有验证。以工程标准看这是一个自研算法亮点。

### 3.2 局限性

- `P(F)=0`意味着BKT不建模技能遗忘。学生半年前掌握的知识点和昨天掌握的具有相同的P(known)。遗忘只由复习调度器单独处理，两个模型互不通信。
- 全局默认参数对所有知识点一视同仁。现实中"递归"的P(T)应该远低于"变量赋值"的P(T)，但BKT对所有概念使用相同的学习转移概率。
- 概念名规范化 (行1194-1246) 依赖KG词汇表。词汇表从JSON文件静态加载（行1149-1172），运行时不更新。新上传的教材不会自动扩充词汇表。

## 四、混合检索 — 企业级架构

### 4.1 检索流水线 (rag_service.py:280-370)

```
查询 → FAISS Dense(BGE-M3)  ─┐
      → BM25 Sparse(jieba)  ─┤
                              ├→ RRF融合(k=60) → CrossEncoder精排(BGE-Reranker-v2) → Top-K
                              │
                              └→ 降级: ChromaDB直接检索 (FAISS不可用时)
```

**实际使用的模型：**
- Embedding: BAAI/bge-m3（稠密1024维+稀疏lexical双向量）
- Reranker: BAAI/bge-reranker-v2-m3（CrossEncoder架构）

这个架构与HuggingFace的MTEB排行榜上企业级RAG系统的设计一致。RRF（Reciprocal Rank Fusion）参数k=60是文献中的标准值。

### 4.2 性能优化（已修复）

- BM25索引从每次请求重建改为初始化时构建一次（`_bm25_model`缓存）。对10K+文档的语料库，这个修复将BM25检索从O(N²)降到O(N)。
- FAISS子索引发现从每次glob改为首次扫描后缓存（`_faiss_discovered`集合）。
- CUDA不可用时自动回退CPU（行104-108），无需手动改配置。

### 4.3 局限性

- `rag_trace` (行278-350) 和 `hybrid_search` (行280-370) 是两套独立实现。`rag_trace`为前端可视化增加了阶段计时和统计信息，但检索逻辑重复。修改检索策略时需要改两处。
- BGE-M3模型首次加载需要数分钟（模型文件约2GB）。虽然有超时和降级机制，但首次请求的用户会遇到15秒超时后返回空结果的情况。
- 习题检索`search_exercises` (行450-500) 使用独立的检索路径，不经过RRF融合和CrossEncoder精排。

## 六、数据流完整性

### 6.1 实际闭环

```
Profile Agent采集 → knowledge_base写入MySQL
    ↓ sync_profile_to_bkt
BKT初始化先验P(L₀)
    ↓ record_answer (贝叶斯更新)
BKT掌握状态更新
    ↓ get_mastered()
Path Agent拓扑排序 → 教学流程
    ↓ resource_agent生成内容
Content Store / RAG检索 → 注入知识
    ↓ record_review
复习调度器更新间隔
```

### 6.2 断裂点

1. **BKT→Path的概念名对齐**：已在P0修复中在`record_answer`入口添加`normalize_concept_name`调用。但KG词汇表静态加载，新概念无法自动对齐。

2. **复习调度器无主动推送**：`get_due_reviews()` (review_scheduler.py:197) 返回应复习的概念列表，但只有Path Agent主动调用时才展示。没有定时任务、没有SSE推送、没有前端轮询。

3. **Profile维度分与BKT后验的不一致**：profile_agent的`_compute_dimension_scores`给出的knowledge_score（基于自报话题数×12+关键字加分）与BKT的真实贝叶斯后验是两套完全不同的评分体系。Dashboard同时展示两者时可能出现"profile说知识掌握90分但BKT说P(known)=0.3"的矛盾。

## 八、代码卫生

### 8.1 好的模式

- SQLAlchemy 2.0 `Mapped`注解风格全项目统一
- BKTState和ReviewSchedule的`(user_id, concept)`唯一约束防止重复数据
- 前端`marked`+`DOMPurify.sanitize`正确防御XSS
- 速率限制中间件（`rate_limit.py`）使用滑动窗口+令牌桶，区分认证/匿名用户
- ChromaDB HTTP客户端使用单例模式+连接池

### 8.2 待改进

- `chat.py` 1061行的单体文件——SSE流式+持久化+事件钩子+画像采集全部混在一个文件里
- `supervisor.py`的`supervisor_node`函数320行——过长，难以单独测试路由逻辑
- `path_agent.py`的`path_agent_node`函数339行——同样的单体函数问题
- knowledge_base在dict↔string之间的类型转换分布在3个不同文件中
- `chat.py`和`conversation.py`共享`/api/chat`路由前缀——维护时容易造成路由冲突

## 十、总结

### 核心竞争力

1. **BKT贝叶斯知识追踪**：四参数模型实现正确，EM拟合采用坐标下降+多起点搜索，测试有手算验证。这是系统中质量最高的模块。
2. **混合检索流水线**：Dense+BM25→RRF→CrossEncoder的企业级架构，且有`rag_trace`可视化端点。
3. **前端四态覆盖**：所有数据页面都处理了loading/error/empty/data，是良好的工程实践。
4. **规则+LLM混合路由**：比纯LLM路由更经济可靠。

### 主要短板

1. **API/Agent零测试**：10个路由模块和7个Agent函数完全没有测试覆盖。
2. **数据流对齐依赖手动同步**：BKT↔Profile↔KG三个系统的概念名需要`normalize_concept_name`手动对齐，且词汇表静态加载。
3. **复习系统无主动推送**：复习提醒只在Path Agent执行时被动展示，无定时任务或SSE推送。
4. **两个单体函数过长**：`supervisor_node`(320行)和`path_agent_node`(339行)需要拆分。
5. **前端无移动端适配**：全部为桌面端设计。
