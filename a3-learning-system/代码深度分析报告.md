### 1.2 Agent 路由流程

\\\
用户输入 → Supervisor (keyword-first + LLM fallback)
    ├─ profile → profile_agent
    ├─ resource → collaborative_resource (并行: Resource + Quality)
    ├─ question → collaborative_qa (并行: Question + Evaluation)
    ├─ path → collaborative_path (并行: Path + Resource)
    ├─ evaluation → evaluation_agent
    └─ chat → chat_agent → END

各 Worker 执行完毕后返回 Supervisor
Supervisor 判断继续下一轮或 END

## 二、官网要求逐条对标分析

### 2.1 对话式学习画像自主构建（6+维度）

| 官网要求 | 代码实现 | 状态 |
|---------|---------|:----:|
| 知识基础 | profile_agent.py: knowledge_base, LLM抽取+结构化dict | ✅ |
| 认识风格 | profile_agent.py: cognitive_style (visual/auditory/kinesthetic/reading) | ✅ |
| 学习目标 | profile_agent.py: learning_goal (exam/skill/career/interest) | ✅ |
| 每周时间 | profile_agent.py: weekly_hours, 自然语言提取→float | ✅ |
| 偏好资源 | profile_agent.py: preferred_resource_type (video/text/code/interactive) | ✅ |
| 易错模式 | profile_agent.py: error_patterns, LLM提取+持久化 | ✅ |

**漏洞与修改点：**

1. **维度刚好6个，无冗余** — 官网要求"不少于6个维度"，代码恰好6个。建议增加1-2个维度（如 learning_phase 学习阶段、interest_direction 兴趣方向），确保安全冗余
2. **_compute_dimension_scores 引用未定义** — profile_agent.py 第34行调用了 _compute_dimension_scores(profile)，但该函数未在本文件中定义。实际在 evaluation_agent.py 中才进行维度分数计算。这行代码在运行时会抛出 NameError ❗
3. **BKT 同步可能吞错误** — profile_agent.py 第76行 sync_profile_to_bkt(user_id, kb) 被 try/except 包裹，如果 BKT 表结构不匹配或 concept 字段异常，错误会静默丢失，用户不知道画像没同步成功
4. **cognitive_style 和 preferred_resource_type 问题重复** — DIMENSION_QUESTIONS 中第6个问题（error_patterns）和第4个问题（cognitive_style）在语义上可能重叠，学生容易混淆

### 2.2 多智能体协同的资源生成（5+种类型）

| 官网要求 | 代码实现 | 状态 |
|---------|---------|:----:|
| 多智能体架构 | Supervisor + 6 Agents + 3种协同模式 | ✅ |
| 5种资源类型 | document / mindmap / question_set / code_example / video_script | ✅ |
| 并行协同 | collaborative_qa / collaborative_resource / collaborative_path | ✅ |
| 防幻觉机制 | content_guard.py + resource_agent.py 9条反幻觉铁律 | ✅ |

**漏洞与修改点：**

1. **comparison 类型飘在 TYPE_LABELS 但未被生产** — resource_agent.py 顶部 TYPE_LABELS 定义了 "comparison": "对比分析"，但类型枚举（注释中的4种）和实际代码逻辑都不产出 comparison 类型。建议要么实现 comparison 分支，要么删除这个 label
2. **video_script 缺乏评测标准** — 虽然声明支持视频脚本生成，但 resource_agent.py 的 prompt 中缺少对视频脚本的格式和长度要求描述
3. **quality_reviewer 评分无区分度** — collaboration.py _quality_review_node 中：score = max(40, 100 - len([i for i in issues if not i.startswith('[')]) * 15)。issues 包含4条以上提示语（BKT建议、格式要求、风格提示、结构要求），去掉 [xxx] 前缀后至少有3条有效 issues → score = 100-3*15=55，最差也就是 100-4*15=40。永远在 40-55 分之间跳动，跟没评一样
4. **RESOURCE_PROMPT 超长** — 资源 agent 的 prompt 包含9条"铁律" + 详细的格式模板 + 画像数据 + 参考文献，总长度可能超过4000字。Spark API 对 prompt 长度敏感，可能导致超时或截断
5. **ThreadPoolExecutor 并行可能回退** — collaboration.py 的 COLLABORATION_TIMEOUT=30秒。讯飞 API 的真实调用在高峰期可能超过30秒，导致并行失败退回串行

### 2.3 个性化学习路径规划和资源推送

| 官网要求 | 代码实现 | 状态 |
|---------|---------|:----:|
| KG拓扑路径 | 自研 KG 算法（TF-IDF→共现分析→DAG→拓扑排序） | ✅ |
| BKT动态调整 | supervisor.py 闭环检测 + 自动 replan | ✅ |
| 间隔重复复习 | review_scheduler.py + path_agent.py Ebbinghaus 计算 | ✅ |
| 个性化调度 | dynamic_path_planner.py（含 weekly_hours 参数） | ✅ |
| 资源推送 | 前端 ResourceView + LearningPathView | ⚠️ |

**漏洞与修改点：**

1. **_select_domain_files 映射缺陷** — path_agent.py 中 "go" 关键词映射到 kg_go.json。由于 if kw in topic_lower 是子串匹配，输入"go"、"golang"、"mongo" 都会匹配到 Go 语言 KG。但 "mongo" 应该匹配数据库，这是一个明显的误匹配
2. **无匹配时加载全部 KG** — _load_multidiscipline_kg 中，当 _select_domain_files 返回空列表时，会加载 docs/ 目录下全部 kg_*.json 文件。如果学生说"学C++"但关键词没匹配到，就会输出前后端+算法+网络+数据库的混乱混合体
3. **INTERVALS 常量需对齐** — path_agent.py 和 review_scheduler.py 各自使用间隔重复参数。review_scheduler.py 中 INTERVALS = [1, 3, 7, 14, 30, 90]，path_agent.py 中硬编码 intervals = [1, 3, 7, 14, 30]，少一个 90 天。应该统一引用
4. **前端 DAG 渲染待确认** — LearningPathView.vue 34671字节，是否需要检查实际渲染的 DAG 图是用 vue-flow 还是 ECharts 力导向图
5. **资源推送缺失主动机制** — 目前前端 ResourceView 是被动展示资源的列表页，缺少主动推送（如消息卡片的推荐按钮、Dashboard 的"今日推荐"区域）

### 2.4 智能辅导（可选加分项）

| 官网要求 | 代码实现 | 状态 |
|---------|---------|:----:|
| 即时答疑 | Chat Agent + Resource Agent 配合 | ✅ |
| 多模态解答 | 文字 + 代码 + Mermaid图表 + 图片上传 | ✅ |
| 短视频讲解 | 仅 video_script 文本脚本，未生成视频 | ❌ |

**漏洞与修改点：**

1. **图片上传渲染确认** — ChatRequest.images 字段接收 base64 图片，但 ChatMessage.vue 需要能渲染 image/* 类型的消息。需确认前端是否支持 \<img\> 标签的 base64 显示
2. **缺少真正的视频/动画生成** — video_script 只生成文本脚本。如果要达到"多模态短视频讲解"，需要调用视频生成 API（如讯飞 SeeDance）或至少提供一个嵌入视频链接的占位

### 2.5 学习效果评估（可选加分项）

| 官网要求 | 代码实现 | 状态 |
|---------|---------|:----:|
| 多维度评估 | evaluation_agent.py: 6个维度（knowledge/speed/practice/focus/logic/trend） | ✅ |
| BKT知识追踪 | bkt_service.py v4（标准4参数 + EM拟合 + 分步公式展示） | ✅ |
| 动态调整 | supervisor.py: 薄弱维度检测 → 自动触发路径重规划 | ✅ |

**漏洞与修改点：**

1. **Mermaid 饼图重复生成** — evaluation_agent.py 的 EVALUATION_PROMPT 要求 LLM 输出 Mermaid 饼图。但代码注释说"饼图由 chat.py 在流式结束后统一追加"。如果两端都做，前端会看到两块同样的饼图。需要确认实际逻辑
2. **中文 Mermaid label 兼容性** — Prompt 中饼图 label 为 "已掌握(p≥0.85)" 等中文，前端 mermaid.js 渲染中文 label 有时会排版异常
3. **BKT速度缓存 TTL 过长** — _speed_cache 的 TTL=300秒（5分钟）。如果学生在5分钟内连续答题，速度分不会更新，评估报告可能滞后
4. **新用户维度分数默认50** — BKT 需要≥10条记录才做 EM 拟合，否则所有维度分数默认 50/100。建议在报告顶部标注"数据不足，评估结果仅供参考"
5. **代码中引用未定义的变量** — _compute_speed_score 的 fallback 逻辑中 score = 50 但该值未通过 _speed_cache 缓存直接返回。少量影响

## 七、结论

项目整体代码质量不错，核心的多智能体架构、BKT v4 算法、自研知识图谱都是亮点。主要问题集中在：

1. 画像维度刚好擦边（>=6→正好6），缺少冗余维度，且有未定义函数的 bug
2. 部分辅助函数逻辑过于简单（quality_reviewer score 计算、学科文件映射）
3. 前端无测试覆盖
4. "生成进度追踪"未在前端实现（影响评分中的用户体验项）
5. 缺少比赛要求的完整文档和演示物料
